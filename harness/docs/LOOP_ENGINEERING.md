# Loop Engineering

코딩 작업을 계획부터 원격 반영까지 반복 가능하게 처리하는 공통 절차입니다.
`model_test_pc`에는 자동 적용하지 않으며, 공통 하니스와 다른 프로젝트에 적용합니다.

## 기본 루프

```text
요구사항 → PLAN → EXECUTE → VERIFY
                         ↓ 실패
                 원인 수정 → VERIFY 재실행
                         ↓ 통과
                 diff/보안 확인 → commit → push
```

1. 요구사항과 영향을 받는 파일을 확인하고 `PLAN.md`에 범위, 인수 조건,
   테스트, 위험을 기록합니다.
2. 계획된 범위 안에서만 소스를 수정합니다.
3. 프로젝트의 테스트, 빌드, 린트, 보안 검사를 실행합니다.
4. 검증이 실패하면 실패 원인을 수정하고 같은 검증을 다시 실행합니다.
   기본 반복 상한은 5회입니다.
5. 모든 검증이 통과하면 `git diff`, `git status`, 비밀정보, 대용량 산출물을
   확인하고 `VERIFICATION.md`에 결과를 기록합니다.
6. 커밋 후 현재 브랜치의 원격 저장소로 push합니다.

## 자동 중단 조건

다음 상황에서는 수정·커밋·push를 계속하지 않고 사용자 확인을 요청합니다.

- 테스트·빌드·린트·보안 검사 실패가 반복 상한에 도달함
- merge conflict, 원격 변경, 인증 만료 또는 push 권한 부족
- `.env`, token, API key, private key, 비밀번호 등 비밀정보 발견
- 작업 범위를 벗어난 변경, 예상하지 못한 삭제, 대용량 산출물 발견
- 운영 데이터 삭제, 서비스 재시작, 권한 변경 등 되돌리기 어려운 작업 필요
- 대상 브랜치·원격 저장소·커밋 범위가 불명확함

## 웹 인증

GitHub CLI가 설치되어 있고 인증이 필요할 때만 다음을 실행합니다.

```sh
gh auth login --web
gh auth status
```

인증 코드는 사용자가 브라우저에서 직접 입력합니다. 인증이 확인된 뒤에도
push 대상과 변경 범위를 다시 확인합니다. 인증 토큰은 파일이나 로그에 기록하지 않습니다.

## 커밋 규칙

```text
<type>: <짧은 변경 내용>
```

예: `docs: synchronize project source of truth`

검증 통과 전에는 commit과 push를 수행하지 않습니다. 자동 루프는 인증·충돌·보안·
파괴적 변경을 대신 판단하지 않습니다.
