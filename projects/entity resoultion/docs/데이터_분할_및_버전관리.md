# 지식 그래프 데이터 분할 및 버전관리

## 파일 구조

```text
src/data/knowledge-graph/              # 관리 원본
├─ manifest.json
├─ nodes/
│  ├─ structure.json          # 제품유형, 파트, 구성품, 도메인, 공정
│  ├─ materials.json          # 물질개념, 참조물질
│  ├─ terminology.json        # 라벨, 표기형태, 식별자, 한정자, 규격코드
│  └─ other.json
├─ edges/
│  ├─ structure.json
│  ├─ materials.json
│  ├─ terminology.json
│  └─ reference-mappings.json # BRIDGES_TO 및 ref_id 매핑
└─ versions/
   └─ baseline.json

public/data/knowledge-graph/           # 브라우저 조회용 생성본
```

화면은 더 이상 파트명이 포함된 단일 JSON 파일을 읽지 않고 `manifest.json`을 기준으로 위 파일들을 함께 읽습니다. 제품이나 파트가 추가되어도 파일명은 고정되며, 해당 유형의 파일만 변경하면 됩니다.

## 항목 단위 버전관리

- 모든 분리 항목과 관계에 `revision: 1`, `updated_at` 기준값을 부여했습니다.
- 화면에서 수정·추가·삭제한 이력은 브라우저의 `entity-resolution-history`에 항목/관계 ID별로 저장됩니다.
- 수정 이력은 대상 ID, 작업 종류, 상세 내용, 시각을 보관합니다.
- 정적 JSON만으로는 여러 사용자의 동시 수정, 승인, 되돌리기를 안전하게 처리할 수 없습니다.

## 운영 전환 권장안

1. 현재 JSON 분할 구조를 API의 읽기 모델로 사용합니다.
2. 수정 요청은 API에서 `item_id`, 현재 `revision`, 변경값을 함께 받습니다.
3. 서버는 revision이 일치할 때만 저장하고, 성공 시 revision을 1 증가시킵니다.
4. 이전 값·이후 값·수정자·수정 시각을 `entity_revision` 테이블 또는 append-only JSONL에 기록합니다.
5. 승인된 배포 시에만 분리 JSON과 `manifest.json`의 `data_version`을 올립니다.

이 방식이면 단일 대용량 파일 충돌을 피하고, 특정 파트·물질·참조 매핑만 독립적으로 검토하고 되돌릴 수 있습니다.
