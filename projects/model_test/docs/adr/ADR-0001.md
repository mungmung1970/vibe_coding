# ADR-0001 · 콘솔 서버와 서빙 엔진의 분리

상태: 채택됨
결정일: 2026-09-07 (구현 시점 기준 소급 기록)
관련: docs/spec/SPEC.md F1, docs/sot/SOT.md

## 맥락

로컬 모델 여러 개를 번갈아 서빙하며 파라미터를 바꿔 응답을 비교하는 콘솔이 필요했다. 제약은 세 가지였다.

1. 실행 환경의 torch는 NVIDIA 컨테이너 빌드(`2.10.0a0+...nv25.12`)다. PyPI 패키지가 이를 덮어쓰면 컨테이너 환경이 손상된다.
2. GPU는 B200 1장이다. 여러 모델을 동시에 올릴 수 없다.
3. 모델 로딩은 수 분이 걸리고 실패할 수 있다. 그동안 화면은 살아 있어야 한다.

## 결정

**콘솔 서버와 모델 서빙을 별도 프로세스, 별도 파이썬 환경으로 분리한다.**

- 콘솔 서버(`src/backend`)는 파이썬 **표준 라이브러리만** 사용한다. 추가 의존성이 없으므로 실행 환경을 오염시키지 않고, 어떤 파이썬 3.12에서도 그대로 돈다.
- vLLM은 프로젝트 루트의 격리된 가상환경 `.venv-vllm`에 설치한다. 콘솔은 그 인터프리터로 **자식 프로세스**를 띄우고 OpenAI 호환 HTTP로만 통신한다.
- 서빙 수명주기는 `services/serving_manager.py`의 상태 기계(`idle/starting/ready/stopping/error`)가 단독으로 관리하며, "동시에 최대 한 모델"을 잠금과 세대 번호로 강제한다.
- 엔진은 인터페이스(`services/engines.py::Engine`)로 두어 프로세스 관리와 추론 호출을 분리한다.

## 근거

| 대안 | 기각 사유 |
| --- | --- |
| 콘솔 프로세스 안에서 vLLM을 라이브러리로 임포트 | 모델 로딩·크래시가 콘솔을 통째로 죽인다. 모델 교체 시 프로세스 재시작이 필요하고, 콘솔이 vLLM의 무거운 의존성 트리를 그대로 짊어진다 |
| FastAPI/uvicorn 도입 | 편의는 늘지만 실행 환경에 의존성을 추가해야 한다. 필요한 것은 라우팅·JSON·SSE뿐이라 표준 라이브러리로 충분했다 |
| vLLM을 시스템 파이썬에 설치 | NVIDIA torch 빌드를 덮어쓸 위험이 크다 |
| 여러 모델 상시 서빙 | GPU 1장에 들어가지 않는다 |

## 결과

**좋은 점**

- 모델이 죽어도 콘솔은 살아 있고, 상태와 로그로 원인을 보여줄 수 있다(실제로 gpt-oss 첫 기동 실패를 이 경로로 진단했다).
- 콘솔 테스트가 GPU 없이 돈다. 엔진 인터페이스에 테스트 대역(`tests/support.py::StubEngine`)을 끼우면 API 전체를 왕복 검증할 수 있다.
- vLLM 버전 교체가 콘솔과 무관하다. `.venv-vllm`만 갱신하면 된다.

**비용**

- 모델 교체마다 프로세스 재기동이 필요하다(3~13분). 예열 상태를 잃지 않도록 전환은 사용자 조작으로만 일어난다.
- 콘솔이 HTTP·SSE·정적 서빙을 직접 구현한다(`app/core/http.py`). 이 코드는 프레임워크 대신 우리가 유지보수한다.
- 두 파이썬 환경을 관리해야 한다. `engine=auto`가 `.venv-vllm`을 탐색해 이 복잡도를 감춘다.

## 관련 결정

- 대체(mock) 엔진을 두지 않는다. vLLM이 없으면 가짜 답변을 만드는 대신 기동을 거부한다. 초기에 두었던 mock 엔진이 실제 응답으로 오인되는 사고가 있었고, 테스트 대역은 테스트 코드 안에만 둔다.
