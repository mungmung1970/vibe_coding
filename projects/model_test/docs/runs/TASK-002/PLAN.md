# TASK-002 · PLAN — 사고 과정 진행 가시화

작성일: 2026-09-07
근거 SPEC: docs/spec/features/FEAT-002-thinking-progress.md
상태: 승인 대기 (EXECUTE 미착수)

## 1. 문제

추론 모델이 사고 토큰을 생성하는 동안 답변 패널이 12.6초간 정지한 것처럼 보인다. 원인은 기능 결함이 아니라 표시 공백이다 — `enable_thinking` 기본 켜짐 + `show_thinking` 기본 꺼짐의 조합에서 화면에 반영할 신호가 없다.

## 2. 범위

포함
1. 답변 패널에 사고 진행 표시(경과 시간·누적 글자 수) 추가
2. `show_thinking` 설정에 따른 사고 내용 노출 분기 유지 및 진행 표시 병행
3. 완료 통계에 사고 토큰 수 추가
4. 기능 명세(FEAT-002)와 실행·검증 기록 문서화

제외
- 파라미터 기본값 변경, 백엔드/엔진/API 변경, 결과 조회 화면 변경
- gpt-oss-120b 기동 실패 원인 규명(별도 작업)
- `thinkingcap-qwen3.6-27b` 등록 유지/삭제 결정(사용자 확인 필요)

## 4. 설계 방안 비교

| 안 | 내용 | 판단 |
| --- | --- | --- |
| A | `show_thinking` 기본값을 켬으로 변경 | 반려 — 한 줄로 끝나지만 답변 영역이 사고 과정으로 채워져 기본 사용성이 나빠지고, SPEC 비요구사항과 충돌 |
| B | 사고 델타 수신 중 진행 표시(경과·글자 수)만 노출 | **채택** — 정지 상태와 구별되고 사고 내용 노출 정책은 그대로 유지 |
| C | 접힌 thinking 블록을 두고 클릭 시 펼침 | 보류 — B로 문제는 해소되며, 접기/펼치기 상태 관리가 늘어난다. 필요해지면 후속 작업 |

`answer.reasoning`은 이미 상태에 누적되고 스트리밍 중 60ms 간격으로 화면에 반영되므로, 새 상태 필드 없이 기존 값만으로 구현한다. 진행 문구 생성은 순수 함수로 분리해 DOM 없이 테스트한다.

## 5. 인수 조건

| # | 조건 | 확인 방법 |
| --- | --- | --- |
| AC1 | reasoning 델타 수신 중 답변 영역에 사고 진행 표시가 나타난다 | 실제 브라우저(CDP) 실측, 첫 표시 2초 이내 |
| AC2 | `show_thinking=false`에서 사고 **내용**은 노출되지 않는다 | 브라우저 DOM 검사 — thinking 블록 hidden 유지 |
| AC3 | `show_thinking=true`에서 사고 내용이 실시간 표시된다 | 브라우저 DOM 검사 |
| AC4 | 첫 본문 델타 이후 진행 표시가 사라지고 답변이 렌더된다 | 브라우저 DOM 검사 |
| AC5 | 완료 통계에 사고 토큰 수가 표시된다(값이 있을 때만) | 단위 테스트 + 브라우저 확인 |
| AC6 | 기존 동작 회귀 없음 | 프론트 11건 + 백엔드 37건 통과 |

## 6. 테스트

- 단위(node:test): 진행 문구 함수 — 사고 중/본문 시작 후/사고 없음/토큰 수 유무 4가지
- 통합(실제 브라우저, CDP 실시간): `qwen3.8-27b` 서빙 상태에서 프롬프트 실행 후 AC1~AC5 확인
- 회귀: `sh src/frontend/tests/smoke.sh`, `python3 -m unittest discover -s tests -t .`

## 7. 위험

| 위험 | 대응 |
